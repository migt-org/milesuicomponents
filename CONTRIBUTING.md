## Setup

The canonical repository is `migt-org/milesuicomponents`. Contributors work from a fork.

```bash
git clone git@github.com:migt-org/milesuicomponents.git
cd milesuicomponents
git remote add upstream git@github.com:migt-org/milesuicomponents.git
npm ci
npm run storybook
```

Storybook opens at <http://localhost:6006>. Use the **Theme** toolbar button to switch between light and dark mode, and the **Accessibility** panel to check each story.

Use Node 24 (the version CI runs).

## Project structure

```
milesuicomponents/
├── src/
│   ├── index.ts                  Public entry point; every component is exported here
│   ├── components/
│   │   ├── Button.tsx            Component
│   │   ├── Button.test.tsx       Unit + accessibility tests
│   │   ├── Button.stories.tsx    Storybook stories
│   │   └── ...
│   ├── styles/styles.css         Design tokens + all component styles (in @layer miles)
│   ├── utils/cx.ts               Class-name helper
│   └── test/                     Test setup and helpers
├── .storybook/                   Storybook config (theme toolbar, a11y addon)
├── .changeset/                   Pending release notes
├── .github/workflows/
│   ├── ci.yml                    Checks on every PR
│   └── node.js.yml               Release: version PR, npm publish, git tag
├── tsup.config.ts                Build config (outputs dist/)
└── package.json
```

`dist/` is generated by `npm run build` and is the only folder published to npm. Never edit or commit it.

## Scripts

| Command                   | What it does                                       |
| ------------------------- | -------------------------------------------------- |
| `npm run storybook`       | Develop components in isolation                    |
| `npm test`                | Run unit and accessibility tests once              |
| `npm run test:watch`      | Run tests on file changes                          |
| `npm run typecheck`       | Type-check with `tsc`                              |
| `npm run lint`            | ESLint                                             |
| `npm run format`          | Format everything with Prettier                    |
| `npm run build`           | Build `dist/` (JS, types, CSS)                     |
| `npm run build-storybook` | Static Storybook build                             |
| `npm run changeset`       | Describe your change for the changelog and version |

CI runs format check, lint, typecheck, tests, build, `npm pack --dry-run`, and the Storybook build on every PR. Run them locally before pushing.

## How to build a component

Use `src/components/Button.tsx` as your template. Example: a `Badge`.

### 1. Create the component

`src/components/Badge.tsx`:

```tsx
import { forwardRef, type ComponentPropsWithoutRef } from "react";
import { cx } from "../utils/cx";

export type BadgeProps = ComponentPropsWithoutRef<"span">;

const Badge = forwardRef<HTMLSpanElement, BadgeProps>(function Badge(
  { className, ...props },
  ref,
) {
  return <span ref={ref} {...props} className={cx("miles-badge", className)} />;
});

export default Badge;
```

The rules this pattern encodes:

- **PascalCase file name** matching the component name, `.tsx`.
- **Props type** extends the native element's props with `ComponentPropsWithoutRef<"element">`, and is exported as `<Name>Props`. Add custom props with `&` (see `Loader.tsx`).
- **`forwardRef`** with a named function, so refs work on React 18 and 19 and DevTools shows the name.
- **Spread `{...props}` first, then `className`** last, combined with `cx("miles-<name>", className)`. The base class can never be lost, and `style`, `children`, and event handlers pass through automatically.
- **Accessible defaults go before the spread** (e.g. `role="status"` in `ResponseStatus`), so consumers can still override them.
- **No CSS import** in the component. All styles ship in the single stylesheet.
- **Use the most semantic element**: `button` for actions, `a` for navigation, `h1`–`h6` for headings, `ul`/`li` for lists, `dialog` for modals.
- **No hooks or browser APIs** unless needed. If a component needs state or effects, add `"use client";` as the first line of its file so it works in Next.js Server Components.

### 2. Add the styles

Add a labeled section to `src/styles/styles.css`, **inside** the `@layer miles { … }` block, using tokens only:

```css
/* ---------------------- Badge ---------------------- */
.miles-badge {
  display: inline-block;
  padding: 0.2em 0.6em;
  font-size: var(--miles-font-size-small);
  color: var(--miles-primary-color);
  background-color: var(--miles-tertiary-color);
  border-radius: var(--miles-border-radius);
}
.miles-badge.success {
  color: var(--miles-success-color);
}
```

- Root class: `miles-` + kebab-case component name. Child classes: `miles-<name>-<part>`.
- Variants are **compound** selectors on the root (`.miles-badge.success`). A space (`.miles-badge .success`) targets a child instead.
- New colors need a `--miles-` token in `:root` **and** a dark value in `[data-theme="dark"]`.
- Prefix animation names too (`@keyframes miles-pulse`).

### 3. Export it

In `src/index.ts`:

```ts
export { default as Badge, type BadgeProps } from "./components/Badge";
```

### 4. Write tests

`src/components/Badge.test.tsx`. At minimum, test that it renders the right element with the base class plus a custom `className`, that it forwards `ref` and native props, and that it has no accessibility violations:

```tsx
import { render, screen } from "@testing-library/react";
import { expectNoA11yViolations } from "../test/axe";
import Badge from "./Badge";

describe("Badge", () => {
  it("renders with the base class", () => {
    render(<Badge className="success">Done</Badge>);
    expect(screen.getByText("Done")).toHaveClass("miles-badge", "success");
  });

  it("has no accessibility violations", async () => {
    const { container } = render(<Badge>Done</Badge>);
    await expectNoA11yViolations(container);
  });
});
```

### 5. Write stories

`src/components/Badge.stories.tsx`, with one story per variant:

```tsx
import type { Meta, StoryObj } from "@storybook/react-vite";
import Badge from "./Badge";

const meta = {
  title: "Components/Badge",
  component: Badge,
  args: { children: "New" },
} satisfies Meta<typeof Badge>;

export default meta;
type Story = StoryObj<typeof meta>;

export const Default: Story = {};
export const Success: Story = { args: { className: "success" } };
```

Check every story in light and dark mode, and make sure the Accessibility panel shows no violations. It also checks color contrast, which the unit tests can't.

### 6. Test it as a consumer

To check the real published package in an app (such as the sibling `testuicomponents` Next.js app):

```bash
npm pack
cd ../testuicomponents
npm install ../milesuicomponents/milesuicomponents-<version>.tgz
```

This installs exactly what npm users get, so it catches packaging mistakes (a missing export, a file left out of `dist/`).

### 7. Document it and add a changeset

- Add the component to the **Components** table in `README.md`, and remove it from the roadmap.
- Run `npm run changeset`, choose **minor**, and describe the new component.

## Best practices

### Code

- **Generic only.** A component belongs here only if it's useful across Miles projects and has no project-specific naming, content, or layout (no `CourseCard`, `LoginForm`, etc.). Build those in the consuming app from these primitives.
- **One component per file**, small, presentational, and composable. Build complex UI by nesting (`MilesCard` > `Button`).
- **No business logic or data fetching.** Everything comes in through props and `children`.
- **No runtime dependencies** without team agreement. React is a peer dependency; everything else is a dev dependency.
- **Strict TypeScript.** No `any`, no `@ts-ignore`. Export a props type for every component.
- **Don't rename or remove exports, classes, or tokens** in a minor or patch release. Consumers rely on them. If something must change, deprecate it first and remove it in the next major.
- **Formatting** is Prettier's defaults; run `npm run format`.
- **Comments** only where the code can't explain itself (the _why_, not the _what_).

### Styling

- **Tokens over hard-coded values** for colors, font sizes, radii, and shadows.
- **Everything inside `@layer miles`**, so consumer styles always win.
- **Every class, token, and keyframe starts with `miles-`.**
- **Support dark mode** for every new color.
- **No `!important`.**
- Prefer relative units (`rem`, `em`, `%`). If a fixed width is needed, consumers must be able to override it.
- Keep the `/* ---- Component Name ---- */` section headers so the stylesheet stays easy to scan.
- Respect `prefers-reduced-motion` for any animation.

### Accessibility

- Use real interactive elements (`button`, `a`, `input`). Never add `onClick` to a `div`.
- Interactive elements need a visible `:focus-visible` style.
- Decorative icons are `aria-hidden`; icon-only buttons need an `aria-label`.
- Status and toast components use `role="status"` or `role="alert"`.
- Text/background contrast meets WCAG AA (4.5:1 for normal text). Check it in Storybook's Accessibility panel.

### Pull requests

- One component or one fix per PR. Keep PRs small and focused.
- Include a changeset (CI fails without one). For docs- or test-only changes, run `npx changeset --empty`.
- Describe what changed and why, with light and dark screenshots for any visual change.
- All CI checks must pass and at least one reviewer must approve before merging.

## Git workflow

For each change, branch from the latest `upstream/main`:

```bash
git fetch upstream
git checkout -b feat/badge upstream/main
npm run changeset
git commit -m "add Badge component"
git push origin feat/badge
```

Then open a PR from your fork's branch into `migt-org/milesuicomponents:main`.

**Branch names:** `feat/<component>`, `fix/<component>-<issue>`, `docs/<topic>`, `style/<topic>`.

**Commit messages:** short, imperative, lowercase: `add Badge component`, `fix loader wrapper className`, `update toast colors`.

## Releasing

Releases are automated with [Changesets](https://github.com/changesets/changesets). Never edit `version` in `package.json` by hand, and never run `npm publish` locally.

1. Every PR includes a changeset (`npm run changeset`) choosing a [semver](https://semver.org/) bump:
   - **patch**: bug fix or style tweak
   - **minor**: new component or new prop
   - **major**: breaking change (removed or renamed export, class, or token; changed markup that breaks consumer CSS)
2. When PRs merge to `main`, the release workflow opens (or updates) a **Version Packages** PR. It bumps `package.json` and writes `CHANGELOG.md` from the pending changesets.
3. Merging the **Version Packages** PR publishes the new version to npm (via npm Trusted Publishing, with provenance) and pushes a `v<version>` git tag.
